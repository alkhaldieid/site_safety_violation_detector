#+AUTHOR: Eid Alkhaldi, Ph.D.

* Overview

  Binary image classifier for safety violations on worksite images
  (violation / no_violation), built with PyTorch and timm.

  The earlier version of this repo was a notebook prototype with a
  single EfficientNet-B0 and hard-coded paths. I rewrote it as a small
  package so I can retrain, swap architectures, and re-evaluate without
  going back into the notebooks.

  What it does:
  - Loads images with ImageFolder and the usual ImageNet preprocessing.
  - Trains a timm backbone with a small MLP head that returns logits.
  - Optionally trains several candidate architectures and picks the
    best one on validation F1.
  - Evaluates on a held-out test split and saves the metrics.
  - Runs inference on a single image or a folder.

  Standard ImageFolder layout, two classes:

* Installation

  #+BEGIN_SRC bash
  git clone https://github.com/alkhaldieid/site_safety_violation_detector.git
  cd site_safety_violation_detector

  python -m venv .venv && source .venv/bin/activate
  pip install --upgrade pip
  pip install -e ".[dev,plot]"
  #+END_SRC

  ~-e .~ installs the package in editable mode and exposes five
  console scripts: ~safety-train~, ~safety-evaluate~, ~safety-infer~,
  ~safety-sweep~, ~safety-dataset~. The ~dev~ extra adds pytest and
  ruff; ~plot~ adds matplotlib; ~research~ adds ~imagehash~ for
  optional perceptual-near-duplicate detection.

* Configuration

  Configs live in ~configs/~. The fields are grouped by concern:

  - ~data~     dataset paths, image size, batch size, num workers
  - ~model~    architecture (any timm name), pretrained, dropout, hidden dim
  - ~optim~    optimizer (adam / adamw / sgd), LR, weight decay, scheduler
  - ~train~    epochs, early stopping (patience + metric), class weights, grad clip
  - ~eval~     decision threshold + optional threshold search on validation
  - ~runtime~  seed, device (auto / cpu / cuda / mps), output directories
  - ~sweep~    candidate architectures, selection metric, tie-breaker

  Any field can be overridden from the CLI:

  #+BEGIN_SRC bash
  safety-train --config configs/default.yaml \
               --set train.epochs=10 \
               --set optim.learning_rate=3e-4 \
               --set runtime.device=cpu
  #+END_SRC

  Unknown fields raise an error instead of being silently ignored.

* Training a single model

  #+BEGIN_SRC bash
  safety-train --config configs/default.yaml \
               --set data.root=/path/to/Worksite-Safety-Monitoring-Dataset
  #+END_SRC

  Outputs:
  - ~models/<arch>.pt~                — best-epoch checkpoint
  - ~models/<arch>.json~              — sidecar metadata (arch, class names,
                                         image size, threshold, metrics, config,
                                         git commit, timestamp)
  - ~reports/<arch>/history.json~     — per-epoch training history
  - ~reports/<arch>/history.csv~      — same, as CSV
  - ~reports/<arch>/final_metrics.json~ — best-epoch summary and tuned threshold
  - ~reports/<arch>/config.yaml~      — the resolved config used for the run

  Early stopping watches ~train.early_stopping_metric~ (default
  ~val_f1~; also supports ~val_loss~ and ~val_pr_auc~). When
  ~train.use_class_weights~ is true, the positive class weight is
  computed from training counts and passed to BCEWithLogitsLoss as
  ~pos_weight~.

* Training multiple models and picking the best

  #+BEGIN_SRC bash
  safety-sweep --config configs/model_sweep.yaml \
               --set data.root=/path/to/Worksite-Safety-Monitoring-Dataset
  #+END_SRC

  The sweep:
  1. Builds the train + validation loaders once and reuses them, so
     every candidate sees the same split.
  2. Trains each architecture in ~sweep.architectures~.
  3. Records per-model metrics, parameter count, checkpoint size, and a
     rough inference latency.
  4. Writes ~reports/model_comparison.json~ and
     ~reports/model_comparison.csv~.
  5. Picks the winner by ~sweep.selection_metric~ (default ~val_f1~)
     with ~sweep.tie_breaker~ (default ~val_loss~, lower-is-better).
  6. Copies the winning checkpoint to ~models/best_model.pt~ and writes
     ~models/best_model_metadata.json~ with the metrics of all
     candidates and a short note saying which one won and why.

  Default candidates: ~efficientnet_b0~, ~resnet50~,
  ~mobilenetv3_large_100~, ~convnext_tiny~. Override the list with
  ~--set sweep.architectures=...~ or edit the YAML.

* Evaluation

  #+BEGIN_SRC bash
  safety-evaluate --config configs/default.yaml \
                  --checkpoint models/best_model.pt
  #+END_SRC

  ~safety-evaluate~ loads the checkpoint and its sidecar metadata so
  the right architecture and image size are used (whether the
  checkpoint came from ~safety-train~ or ~safety-sweep~). If
  ~eval.search_threshold_on_val~ is true, the decision threshold is
  tuned on the validation set first, then the test split is scored
  with that threshold.

  Outputs go under ~reports/<arch>_test/~:
  - ~test_metrics.json~
  - ~classification_report.txt~ (sklearn-style)
  - ~confusion_matrix.json~

* Inference

  Single image:

  #+BEGIN_SRC bash
  safety-infer --checkpoint models/best_model.pt \
               --input path/to/image.jpg
  #+END_SRC

  Folder:

  #+BEGIN_SRC bash
  safety-infer --checkpoint models/best_model.pt \
               --input path/to/folder \
               --output predictions.csv
  #+END_SRC

  Notes:
  - Image size and normalisation come from the checkpoint's metadata,
    so preprocessing matches training.
  - Threshold defaults to the value stored in the checkpoint; override
    with ~--threshold 0.4~.
  - Broken or unreadable images produce a row with ~error=...~ instead
    of crashing the whole batch.
  - Output goes to stdout by default. Use ~--json~ for machine-readable
    output, or ~--output file.{csv,json}~ to write to disk.

* Tests

  #+BEGIN_SRC bash
  pytest
  #+END_SRC

  Tests use a synthetic ImageFolder dataset created inside a temp
  directory and ~pretrained=False~ for the timm models, so they do not
  need the real dataset and do not download anything. They cover the
  config loader, dataset layout validation, transforms, model
  construction and forward shape, metric computation, threshold search,
  inference preprocessing, and checkpoint metadata round-trips.

* Running without installing

  Each console script has a mirror under ~scripts/~ that prepends ~src/~
  to ~sys.path~, so the pipeline can be used from a fresh checkout:

  #+BEGIN_SRC bash
  python scripts/train.py             --config configs/default.yaml
  python scripts/train_model_sweep.py --config configs/model_sweep.yaml
  python scripts/evaluate.py          --checkpoint models/best_model.pt
  python scripts/infer.py             --checkpoint models/best_model.pt --input some/folder
  #+END_SRC

* Rationale for the Production-Grade Refactor

  The original code worked but was hard to reuse. A few notes on what
  changed and why.

** Hard-coded paths
   ~src/evaluate.py~ used to point at
   ~/data/home/alkhaldieid/repos/site_safety_violation_detector/...~,
   which only existed on one machine. All such paths are now config
   fields (~data.root~, ~runtime.output_dir~, ~runtime.models_dir~,
   etc.) so the same code runs anywhere the dataset is.

** YAML configs
   I wanted to be able to retrain with different hyperparameters
   without editing Python. YAML configs do that, and they get copied
   alongside the run output, so I can tell after the fact what settings
   produced a given checkpoint.

** BCEWithLogitsLoss instead of Sigmoid + BCELoss
   The old model applied ~Sigmoid~ inside ~forward~ and then used
   ~BCELoss~. That combination is numerically unstable when logits get
   large. ~BCEWithLogitsLoss~ does the same job with a log-sum-exp
   internally and is stable. The model now returns logits; sigmoid is
   applied only when computing probabilities for metrics or inference.

** Training multiple models, not just EfficientNet-B0
   The original repo assumed EfficientNet-B0 was the right choice. It
   might be, but I wanted that decided by the data rather than by
   habit. ~safety-sweep~ trains a few candidates on the same split and
   keeps whichever one has the best validation F1. The candidate list
   is editable in the config.

** Validation F1 (or PR-AUC) instead of accuracy
   Accuracy hides class imbalance. If 80% of the images are
   ~no_violation~, a model that always predicts ~no_violation~ scores
   80% accuracy and is useless. F1 (or PR-AUC) reflects both precision
   and recall, so picking by F1 is harder to fool. The selection metric
   is configurable; F1 is the default.

** Checkpoint metadata
   Every checkpoint is saved with a JSON file next to it containing
   the architecture, class-to-index mapping, image size, decision
   threshold, validation metrics, training config, parameter count,
   git commit, and timestamp. ~safety-evaluate~ and ~safety-infer~ load
   from this file, so they always use the preprocessing the model was
   actually trained with.

** Test vs validation metrics
   The validation set is used for early stopping, threshold tuning, and
   model selection. The test set is only touched at the end, with the
   threshold already chosen. They are reported in separate files so I
   don't accidentally tune on test.

** Inference reads metadata
   The same checkpoint might be used in different places. The image
   size, normalisation, and class-name mapping all come from the saved
   metadata, not from a global constant. That way the served model
   can't silently drift from how it was trained.

** Tests
   The non-ML parts (config parsing, layout checks, transforms, metric
   math, threshold search, image-error handling) can be tested without
   a GPU or the real dataset. They are. A failing test catches typos
   long before they show up as a confused training run.

* Model Selection Rationale

  The sweep trains each candidate on the same train/validation split
  with the same loss, optimizer, and scheduler. Each gets the same
  epoch budget and the same early-stopping policy. After all candidates
  are trained, the winner is the one with the highest validation F1
  (ties broken by validation loss).

  The decision is recorded in ~models/best_model_metadata.json~: the
  metrics of every candidate, the chosen metric, the tie-breaker, and
  a short rationale string. The test set is only evaluated on the
  winning model, after selection, so the test metrics are not used to
  pick the model.

  This means the architecture I ship is the one that measured best on
  this dataset under this protocol — not the one that's most popular.

  *Important caveat.* When the sweep is run with a single random seed,
  the selected model is the best one *under that particular dataset
  split, configuration, and seed*. A single run cannot demonstrate that
  the winner is generally superior; another seed could re-order the
  candidates within their noise floor. To estimate seed variance, run:

  #+BEGIN_SRC bash
  safety-sweep --config configs/model_sweep.yaml --seeds 42 123 999
  #+END_SRC

  The sweep then trains every architecture once per seed, reports
  ~mean_val_f1 ± std_val_f1~ across seeds, and selects the architecture
  with the best aggregated mean. The single checkpoint that ships in
  ~models/best_model.pt~ is the best individual seed of the winning
  architecture, but the metadata records the full mean/std table so the
  decision is auditable.

* Research Validity and Reproducibility

  This section is meant to make the methodology defensible for academic
  review.

** Dataset source and expected structure
   The pipeline targets a worksite safety-monitoring dataset organised
   as an ImageFolder with two classes (~violation~, ~no_violation~) and
   three splits (~train~, ~valid~, ~test~) — see the *Dataset layout*
   section above. The dataset itself is not redistributed by this
   repository; point ~data.root~ at the local copy.

** Class distribution reporting
   ~safety-dataset~ writes ~reports/dataset_summary.json~ containing
   per-split / per-class counts and class-balance ratios. Training also
   logs the train-class counts and saves them inside the checkpoint
   metadata under ~train_class_counts~. Use these to report the
   imbalance level alongside accuracy and F1.

** Split strategy and leakage risks
   Splits are taken as-is from the dataset directory layout — the
   pipeline does *not* re-split. This makes the split reproducible
   across machines without storing index files, but it also means
   leakage is the dataset author's responsibility.

   To check for leakage in the local copy, run:

   #+BEGIN_SRC bash
   safety-dataset --check-duplicates
   #+END_SRC

   This computes SHA1 over every image and writes
   ~reports/duplicates.json~ with two sections:
   - ~cross_split~ — files that are byte-identical across two or more
     splits. Any entry here is a *leakage event*: a test image appears
     in training data and inflates test metrics.
   - ~within_split~ — files duplicated inside a single split. These
     don't cause leakage but distort class balance.

   Add ~--check-near-duplicates~ to also run perceptual-hash matching
   (requires the optional ~imagehash~ extra: ~pip install -e ".[research]"~).
   Near-duplicates are softer evidence of leakage — e.g. consecutive
   frames from the same video — but they are worth inspecting.

** Validation set: used for model selection only
   The validation split decides every tunable choice during training:
   when to stop (early stopping), the decision threshold (~eval.search_threshold_on_val~),
   and which architecture wins (in the sweep). Re-using the validation
   split for these decisions is appropriate; it does not bias the test
   metric.

** Test set: held out for final reporting only
   The test split is never looked at during training, threshold tuning,
   or model selection. ~safety-evaluate~ loads the chosen checkpoint
   and scores the test split once, with the threshold already fixed.
   Test metrics are written to ~reports/<arch>_test/test_metrics.json~
   alongside the classification report and confusion matrix, and are
   distinct from the validation metrics stored on the checkpoint.

** Random seed control
   ~set_seed~ seeds Python's ~random~, NumPy, and PyTorch (CPU and CUDA)
   from ~runtime.seed~ before every training run, and sets
   ~torch.backends.cudnn.deterministic=True~ with
   ~torch.backends.cudnn.benchmark=False~. The seed is saved in
   checkpoint metadata so any reported number can be reproduced.

   Note that bit-exact reproducibility on GPUs is *not* guaranteed
   across CUDA versions, driver versions, or hardware. The pipeline
   aims for deterministic behaviour given fixed CUDA/cuDNN versions —
   record the environment (next item) so future runs can be matched.

** Hardware and software reproducibility
   Every checkpoint and sweep report embeds an ~environment~ block
   containing:
   - Python version and executable path
   - Platform / machine / processor / OS
   - CPU count and hostname
   - Versions of every direct dependency (torch, torchvision, timm,
     scikit-learn, numpy, Pillow, PyYAML, tqdm)
   - CUDA availability, device name, CUDA version, cuDNN version
   - MPS availability (Apple Silicon)

   Combined with the git commit (also embedded) this is sufficient to
   reconstruct the exact code + environment that produced a result.

** Metric choice and limitations
   The default selection metric is ~val_f1~, with ~val_loss~ as the
   tie-breaker. F1 is reported because accuracy is misleading under
   class imbalance, and ROC-AUC alone can over-credit models that
   discriminate but predict the wrong calibration. The pipeline
   additionally reports precision, recall, ROC-AUC and PR-AUC; PR-AUC
   is particularly informative when the positive class is rare.

   Caveats every reader should know:
   - F1 depends on the decision threshold; the pipeline tunes the
     threshold on the validation split and freezes it before scoring
     the test split.
   - ROC-AUC and PR-AUC are ~None~ in reports when only one class is
     present in the evaluated batch (the metric is undefined there).
   - A single run's F1 is a point estimate. Use ~--seeds A B C~ to
     report ~mean ± std~ before drawing conclusions across
     architectures.

** Repeated runs across multiple seeds
   Multi-seed reporting is built in:

   #+BEGIN_SRC bash
   safety-sweep --config configs/model_sweep.yaml --seeds 42 123 999
   #+END_SRC

   Each architecture is trained once per seed; the sweep writes:
   - ~reports/model_comparison.json~ — full aggregated + per-run report,
     including a ~rationale~ string that names the seeds used.
   - ~reports/model_comparison.csv~ — one row per architecture (means
     and stds across seeds).
   - ~reports/model_comparison_per_run.csv~ — one row per (arch, seed)
     for inspection.

   The shipped checkpoint is the best individual-seed checkpoint of
   the winning architecture; the metadata records both the aggregated
   ~mean ± std~ and which seed produced it.

** Per-sample error analysis
   ~safety-evaluate~ writes three additional files under
   ~reports/<arch>_test/~:
   - ~misclassified.json~ — every misclassified test image with its
     true label, predicted label, and probability.
   - ~false_positives.json~ — predicted ~violation~, actually ~no_violation~.
   - ~false_negatives.json~ — predicted ~no_violation~, actually ~violation~.

   In a safety-critical setting, false negatives (missed violations)
   are typically more costly than false positives. Reviewing
   ~false_negatives.json~ by hand is the single most useful sanity
   check before claiming the model is "good enough".

** Ethical and safety limitations
   This is a *binary image classifier*. It does not localise
   violations, identify which piece of equipment is missing, or assign
   responsibility. It is not a substitute for a trained safety
   officer.

   Numbers reported on the bundled dataset are not a guarantee of
   field performance: cameras, lighting, occlusion, and demographic
   distribution of subjects all matter. Deployment in any safety- or
   regulatory-critical setting requires re-evaluation on imagery from
   the deployment environment and explicit, documented review of false
   negatives.

   The model can encode biases present in the training data. Before
   deployment, evaluate per-subgroup performance (e.g. site, time of
   day, demographic) where the data permits and report the worst-case
   metric, not just the average.
