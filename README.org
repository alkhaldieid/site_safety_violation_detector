* Overview

  This repository implements a production-grade image-classification pipeline
  for detecting safety violations from worksite images. It is built on
  PyTorch + [[https://github.com/huggingface/pytorch-image-models][timm]] and
  ships with:

  - A reproducible, configuration-driven training loop with early stopping,
    class-imbalance handling, deterministic seeding, and CPU / CUDA / Apple
    MPS device selection.
  - A multi-architecture model sweep that trains several candidates on
    identical data splits and selects the best one by validation F1 (with
    validation loss as the tie-breaker).
  - Test-set evaluation with optional threshold tuning, classification
    reports, and confusion-matrix data saved to disk.
  - Single-image and folder inference that handles corrupt images
    gracefully and loads its own preprocessing from saved metadata.
  - A pip-installable package with console scripts and a pytest test
    suite that runs on synthetic data.

* Problem statement

  The model performs *binary* image classification: ~violation~ vs.
  ~no_violation~ on individual frames from a worksite-safety dataset.

  The motivation is the same as the original notebook prototype: flag
  worksite images where required safety equipment / behaviour is
  missing. This refactor brings the prototype to a state where another
  engineer can reproduce, retrain, and re-evaluate the system without
  guessing hidden paths or running notebook cells.

* Dataset layout

  The pipeline expects the standard ~ImageFolder~ layout:

  #+BEGIN_SRC text
  data/Worksite-Safety-Monitoring-Dataset/
    train/
      violation/
      no_violation/
    valid/
      violation/
      no_violation/
    test/
      violation/
      no_violation/
  #+END_SRC

  The dataset *root* is configured by ~data.root~ in YAML (or via CLI
  ~--set data.root=PATH~). Subdirectory names (~train_subdir~, ~val_subdir~,
  ~test_subdir~) are also configurable for unusual layouts.

  ~data.py~ validates the structure on every run and raises a clear error
  pointing at the missing directory if anything is off.

  Required deps (also in ~requirements.txt~): torch, torchvision, timm,

* Configuration

  All runtime knobs live in YAML files under ~configs/~. The
  configuration is hierarchical (one dataclass per concern):

  - ~data~      — dataset root + split subdirs, image size, batch size, num workers
  - ~model~     — architecture (any timm name), pretrained, dropout, hidden dim
  - ~optim~     — optimiser (adam / adamw / sgd), LR, weight decay, scheduler
  - ~train~     — epochs, early-stopping patience and metric, class-weighting, grad clip
  - ~eval~      — decision threshold + optional validation-threshold search
  - ~runtime~   — seed, device (auto / cpu / cuda / mps), output / models dirs, checkpoint name
  - ~sweep~     — list of candidate architectures, selection metric, tie-breaker

  Any field is overridable from the CLI without editing YAML:

  #+BEGIN_SRC bash
  safety-train --config configs/default.yaml \
               --set train.epochs=10 \
               --set optim.learning_rate=3e-4 \
               --set runtime.device=cpu
  #+END_SRC

  Overrides are typed: ~true / false / null / int / float / scientific~ are
  all coerced. Unknown fields fail loudly so typos surface immediately.

* Training a single model

  #+BEGIN_SRC bash
  safety-train --config configs/default.yaml \
               --set data.root=/path/to/Worksite-Safety-Monitoring-Dataset
  #+END_SRC

  This runs the loop in ~src/site_safety_violation_detector/train.py~,
  saving:

  - ~models/<arch>.pt~                 — the best-epoch checkpoint (state dict
                                          + class names + image size + threshold)
  - ~models/<arch>.json~               — sidecar metadata (config, validation metrics,
                                          parameter count, git commit, timestamp, rationale)
  - ~reports/<arch>/history.json~      — per-epoch training history (loss + all
                                          validation metrics + learning rate)
  - ~reports/<arch>/history.csv~       — same history in CSV form
  - ~reports/<arch>/final_metrics.json~ — best-epoch summary and tuned threshold
  - ~reports/<arch>/config.yaml~       — resolved config used for the run

  Early stopping watches ~train.early_stopping_metric~ (~val_f1~ by default,
  also supports ~val_loss~ and ~val_pr_auc~) with configurable ~patience~.
  When ~train.use_class_weights~ is true, the positive class weight is
  computed from the training-set counts and applied via
  ~BCEWithLogitsLoss(pos_weight=…)~.

* Training multiple models and selecting the best

  #+BEGIN_SRC bash
  safety-sweep --config configs/model_sweep.yaml \
               --set data.root=/path/to/Worksite-Safety-Monitoring-Dataset
  #+END_SRC

  The sweep:

  1. Builds the train / validation dataloaders *once* so every candidate
     sees the same split (no leakage / no inconsistent batch orders).
  2. Trains each architecture in ~sweep.architectures~ end-to-end and
     records per-model metrics, parameter count, on-disk size, and an
     inference-latency estimate (forward passes on a small batch).
  3. Writes a side-by-side comparison report to:
     - ~reports/model_comparison.json~
     - ~reports/model_comparison.csv~
  4. Selects the winner by ~sweep.selection_metric~ (default ~val_f1~) with
     ~sweep.tie_breaker~ (default ~val_loss~, lower-is-better) breaking ties.
  5. Copies the winning checkpoint to ~models/best_model.pt~ and writes
     ~models/best_model_metadata.json~ — including the *rationale*
     ("selected X from N candidates by val_f1=0.…").

  Default candidates: ~efficientnet_b0~, ~resnet50~, ~mobilenetv3_large_100~,
  ~convnext_tiny~. Override with ~--set sweep.architectures=…~ or edit the
  config file.

* Evaluation

  #+BEGIN_SRC bash
  safety-evaluate --config configs/default.yaml \
                  --checkpoint models/best_model.pt
  #+END_SRC

  Evaluation:

  - Loads the checkpoint *and* its sidecar metadata (~best_model_metadata.json~
    or ~<stem>.json~) so the right architecture / image size / class names
    are restored even if the YAML config has drifted.
  - Optionally re-tunes the decision threshold on the *validation* set
    (~eval.search_threshold_on_val~) before scoring the *test* set —
    keeping validation-driven tuning separate from final test scoring.
  - Writes:
    - ~reports/<arch>_test/test_metrics.json~
    - ~reports/<arch>_test/classification_report.txt~  (sklearn report, per-class precision/recall/F1)
    - ~reports/<arch>_test/confusion_matrix.json~

* Inference

  Single image:

  #+BEGIN_SRC bash
  safety-infer --checkpoint models/best_model.pt \
               --input path/to/image.jpg
  #+END_SRC

  Folder:

  #+BEGIN_SRC bash
  safety-infer --checkpoint models/best_model.pt \
               --input path/to/folder \
               --output predictions.csv
  #+END_SRC

  - Preprocessing (image size, normalisation) is reconstructed from the
    saved metadata so it always matches what the model was trained on.
  - Threshold defaults to the value stored in the checkpoint; override
    with ~--threshold 0.4~.
  - Corrupt / unreadable images are reported as a row with ~error=…~ rather
    than crashing the whole batch.
  - Output options: human-readable lines (default), JSON (~--json~), or
    CSV / JSON file via ~--output~.

* Rationale for the Production-Grade Refactor

  The original project trained a single EfficientNet-B0 from a notebook
  with hard-coded paths, a sigmoid baked into the model, and no
  reproducibility scaffolding. The refactor addresses each of those
  weaknesses deliberately.

** Hard-coded paths were removed
   The original ~src/evaluate.py~ pointed at
   ~/data/home/alkhaldieid/repos/site_safety_violation_detector/...~ —
   that path only existed on one machine. The refactor replaces every
   such constant with a configurable field. The dataset root, checkpoint
   names, output directories, image size, and decision threshold all
   come from YAML (with CLI override), so the same pipeline runs on a
   laptop, a workstation, or a CI runner without code edits.

** YAML configuration was added
   A single config object captures everything that affects reproducibility:
   data split locations, batch size, optimizer, learning rate, scheduler,
   epochs, early-stopping patience, decision threshold, device choice,
   and the candidate model list. The config is saved next to every run
   so a year-old result can be re-explained from the artifacts alone.

** ~BCEWithLogitsLoss~ replaced ~Sigmoid~ + ~BCELoss~
   The original model applied ~Sigmoid~ inside ~forward~ and used
   ~BCELoss~. That combination is numerically unstable when logits are
   large (the loss saturates and gradients vanish). PyTorch's
   ~BCEWithLogitsLoss~ folds the sigmoid into the loss with a
   log-sum-exp formulation that is stable everywhere. The new model
   returns *logits*; ~torch.sigmoid~ is applied only when computing
   probabilities for metrics and inference. This change is invisible to
   end users but materially affects training stability.

** Multiple models are now trained instead of assuming EfficientNet-B0 is best
   Picking an architecture by reputation is not science. The sweep
   trains ~efficientnet_b0~, ~resnet50~, ~mobilenetv3_large_100~ and
   ~convnext_tiny~ on identical splits, then ranks them on the validation
   set. Whichever architecture happens to *measure* best on this dataset
   wins, regardless of how popular it is on social media. The candidate
   list is itself configurable, so future contributors can add modern
   backbones without touching the selection logic.

** Validation F1 (with PR-AUC) replaced accuracy as the selection metric
   Accuracy is misleading whenever the classes are imbalanced — a model
   that always predicts "no_violation" can look ≥ 70 % accurate while
   being completely useless. F1 balances precision and recall and is
   more honest under skew; PR-AUC is available as a threshold-free
   alternative. The selection metric is configurable
   (~sweep.selection_metric~) but defaults to ~val_f1~ for this reason.

** Metadata is saved with checkpoints
   Every checkpoint is paired with a JSON sidecar that captures the
   architecture, class-name-to-index mapping, image size, validation
   metrics, parameter count, training config, git commit, timestamp,
   and (for the sweep winner) a written rationale. This is the
   difference between "I trained a model" and "I trained *this* model
   with *these* settings on *that* split". The evaluation and inference
   code load preprocessing parameters from this metadata so models
   trained at, say, 256 × 256 are still evaluated at 256 × 256 even if
   the current config file says otherwise.

** Test metrics are reported separately from validation metrics
   Validation metrics steer training (early stopping, threshold tuning,
   model selection). Test metrics describe how the chosen model is
   *expected* to perform on unseen data. Mixing them is the classic way
   to publish optimistic numbers. The pipeline keeps them separate:
   thresholds are tuned on validation, then frozen, then applied to the
   test split for the final report.

** Inference loads preprocessing and class metadata from saved artifacts
   The same model can be served against multiple deployments; only the
   metadata file is the source of truth for what the model expects
   (image size, normalisation, class index ↔ name mapping, decision
   threshold). ~safety-infer~ reads that file, so the production
   pipeline cannot silently desynchronise from training.

** Unit tests matter even for ML projects
   ML code is not exempt from regressions. The non-ML parts (config
   parsing, layout validation, transforms, metric math, threshold
   search, checkpoint sidecar serialisation, image-error handling)
   absolutely can be tested without GPUs or a real dataset, and they
   are. The test suite catches typos and contract changes long before
   they show up as a confused training run.

* Model Selection Rationale

  This project does *not* pick a model by popularity. It picks one by
  measurement:

  1. ~safety-sweep~ trains each candidate architecture
     (~efficientnet_b0~, ~resnet50~, ~mobilenetv3_large_100~,
     ~convnext_tiny~ — configurable) on the *same* train / validation
     split, with the *same* preprocessing, ~BCEWithLogitsLoss~, optimiser
     and scheduler.
  2. Each run gets the same epoch budget and early-stopping policy.
  3. Per-model artifacts are saved (checkpoint, history, parameter count,
     latency estimate) and aggregated into
     ~reports/model_comparison.{json,csv}~.
  4. The winner is the candidate with the highest *validation* F1
     score, with validation loss resolving ties. The decision is
     auditable: the rationale (which models were compared, which metric
     was used, what the winning value was) is written into
     ~models/best_model_metadata.json~.
  5. The *test* set is only evaluated after the winner has been
     selected, so the test metrics are an unbiased final check rather
     than a tuning signal.

  This makes the selected architecture defensible: "we picked
  ~efficientnet_b0~ because val_f1 = 0.87 vs. 0.84 / 0.82 / 0.85 for
  the alternatives, on identical splits, with the same training
  protocol" — not "everyone uses EfficientNet so we did too".

* Limitations and safety disclaimer

  - The system is a *binary image classifier*. It does not localise
    violations, identify which piece of safety equipment is missing,
    or replace a human safety officer.
  - Real-world deployment requires evaluating on imagery similar to the
    deployment environment (camera angle, lighting, occlusion). Numbers
    on the bundled dataset are not a guarantee of field performance.
  - Decision thresholds should be tuned per deployment to match the
    desired precision / recall trade-off (a high-recall threshold is
    appropriate when missing a violation is more costly than a false
    alarm).
